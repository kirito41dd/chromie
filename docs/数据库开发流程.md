# 数据库开发流程

更新于 2026-11-03。MySQL 8.4、SeaORM 2 与 **schema-first** 已由用户确认并实际接入，sea-orm、sea-orm-migration 与 sea-orm-cli 均使用 2.0.4。已在真实开发库执行迁移，并从数据库反向生成代码。[2.0.4 发布记录](https://github.com/SeaQL/sea-orm/releases/tag/2.0.4)

## 官方流程核验

用户记得的是 SeaORM 的 **schema-first** 流程：先编写 migration，在数据库执行，再从真实表结构生成 Entity。官方迁移文档明确展示这条路径，CLI 支持对 MySQL 进行反向生成。[编写迁移](https://www.sea-ql.org/SeaORM/docs/migration/writing-migration/)、[生成 Entity](https://www.sea-ql.org/SeaORM/docs/generate-entity/sea-orm-cli/)

Chromie 采用 schema-first，以版本化迁移作为表结构的依据。SeaORM 2 也支持 Entity-first，下面保留两者的比较作为选型依据。[Entity-first 官方说明](https://www.sea-ql.org/SeaORM/docs/generate-entity/entity-first/)

## 两种工作流的比较

需要区分两个选择：**从 Entity 还是 migration 开始描述结构**，以及**通过自动同步还是版本化 migration 升级数据库**。Entity-first 可以配合版本化迁移，不能把它的所有方案都等同于服务启动时调用 `sync`。

| 比较维度 | Entity-first | schema-first |
| --- | --- | --- |
| 从零建模和原型迭代 | 手写 Entity，直接表达 Rust 类型与关系，初期步骤更少 | 先写迁移、执行、生成，多一次数据库与生成器往返 |
| 结构与模型的维护 | Entity 是手写结构描述；复杂升级仍要维护迁移，不能保证只改一处 | migration 描述变化，生成模型；需要固定生成选项并保留自定义扩展 |
| 数据库约束与特定结构 | 取决于 Entity 元数据与构建器的表达能力，未覆盖部分通过迁移补充 | 索引、约束及升级顺序直接在迁移中表达，便于审阅数据库影响 |
| 已有数据的演进 | 配合显式迁移也能可靠升级；单靠 `sync` 不足以覆盖完整演进 | 版本化变更天然在主流程中，回填、拆表和删除可明确安排 |
| 可追溯与重放 | 采用迁移及固定 Entity 快照时同样可实现，不是该方案的固有缺点 | 已交付迁移保持不变，生成代码与迁移一起审阅 |
| 使用新 Entity 格式 | 可以使用 | 同样可以使用；选 schema-first 不等于放弃 SeaORM 2 的新模型能力 |

CLI 可以通过 `--entity-format dense` 生成 SeaORM 2 的新 Entity 格式，因而这一格式本身不构成选择 Entity-first 的理由。[官方 Entity 格式说明](https://www.sea-ql.org/blog/2025-10-20-sea-orm-2.0/)

SeaORM 2.0.4 的 `SchemaBuilder::sync` API 明确标注为实验性、行为与签名不受通常的 2.x semver 保证。源码对已有列的类型差异发出告警，不自动修改类型；文档与实现还包含显式列重命名和唯一索引移除，不能将“非破坏性”理解为完全不改变已有结构。[2.0.4 对应源码](https://github.com/SeaQL/sea-orm/blob/2.0.4/src/schema/builder.rs)

官方也展示了在 migration 中使用 `SchemaBuilder::apply` 建表，并保留初始 Entity 的固定快照。它证明 Entity-first 与迁移可以共存，但不意味着当前 Entity 会自动产生完整、可审阅的版本化升级脚本。[Entity 与迁移结合](https://www.sea-ql.org/SeaORM/docs/generate-entity/entity-first/#using-schemabuilder-in-migrations)

选择 **schema-first + Entity 生成**，是因为个人记忆需要长期保留，后续来源拆分、修订关系、空间约束及数据回填需要明确的升级路径；Rust migration 的维护成本也可控。接受的代价是每次结构调整多一步执行与生成。

## 使用边界

| 内容 | 表达与执行方式 |
| --- | --- |
| 表、列、索引、外键及其演进 | `sea-orm-migration` 的 Rust migration，使用其 SeaQuery schema API |
| 持久化实体与模型 | `sea-orm-cli` 生成的 `Entity`、`Model`、`ActiveModel` 与关系定义 |
| 查询、写入、事务及数据迁移 | 通过 SeaORM API 执行 |
| MCP / HTTP 请求响应 | 按接口需要定义结构，与数据库模型显式转换 |

数据库相关实现统一走 SeaORM 套件。不另写同表的手工 Row 映射，不并行维护另一套 ORM 或迁移系统；API 结构也不直接决定表结构。数据库模型不默认整体序列化到外部接口。

## 一次表结构变更

```text
新增 Rust migration
    → 在隔离的开发 MySQL 执行迁移
    → 从数据库生成 Entity / Model / ActiveModel
    → 检查生成差异并调整业务调用
    → 验证新建库与旧版本升级
```

1. 使用 `sea-orm-cli migrate generate <name>` 创建新迁移，编写 `up` 与适用的 `down`，并按顺序加入 `Migrator`。已经交付执行的历史迁移保持稳定，后续变化新增迁移。
2. 在专用开发库执行迁移，使用与实际部署一致的 MySQL 版本和关键配置。迁移描述预期结构，手工修改开发库不能替代迁移。
3. 从该开发库反向生成持久化代码，检查类型、可空性、主键、外键与关系。生成结果纳入版本控制，构建时不要求连接数据库。
4. 在生成文件之外编写业务逻辑；额外关系或自定义行为需要独立保留并检查，不假设数据库能反推出所有领域语义。
5. 验证空库完整执行迁移，以及已有数据从上一版本升级；再次生成不应产生无法解释的差异。数据迁移还要验证数据是否保留、约束是否满足。

当前实际采用以下命令；`DATABASE_URL` 由本地环境安全提供，指向开发库：

Bash：

```bash
./target/debug/chromie-server migrate
.local/tools/bin/sea-orm-cli generate entity --compact-format \
  --date-time-crate time --with-prelude none --output-dir src/entity
cargo fmt --all
```

Nushell：

```nu
^./target/debug/chromie-server migrate
^.local/tools/bin/sea-orm-cli generate entity --compact-format --date-time-crate time --with-prelude none --output-dir src/entity
^cargo fmt --all
```

迁移 crate 位于 `migration/`，生成 Entity 位于 `src/entity/`。当前使用 compact 格式与 `time` 时间类型，不采用 Entity-first 的 schema sync。固定生成器版本和选项，保持 SeaORM、migration 与 CLI 的版本兼容；CLI 默认跳过 `seaql_migrations`。[运行迁移](https://www.sea-ql.org/SeaORM/docs/migration/running-migration/)

## 当前表结构与生成限制

前十张业务表为 `spaces`、`source_events`、`memories`、`memory_revisions`、`memory_sources`、`write_receipts`、`outbox_tasks`、`secrets`、`agent_connections` 和 `agent_credentials`。对象引用、回执及任务使用带 `space_id` 的组合主键 / 外键；跨空间来源关系同时受应用校验和数据库约束保护。生成模型仅作为持久化表示，外部 API 不直接序列化整张表。

第一条迁移创建基础结构。实测 `sea-orm-cli 2.0.4` 依赖的 `sea-schema 0.18.1` 对 MySQL `LONGTEXT` 会生成忽略字段，不能正常反向表示正文。因此第二条迁移把来源正文改为标准 `TEXT`，采集接口上限设为 **60,000 字节**，超长输入直接拒绝，不静默截断。调整前扫描现有数据，发现超过该上限的正文就拒绝执行，保留旧列与数据供人工处理；历史迁移不直接重写。

其他正式记忆正文上限 16,000 字节，更正理由上限 4,000 字节。数据库时间采用 UTC `datetime(6)`；事件重试比较归一到微秒。持久化对象统一由 SeaORM 生成和访问，不通过手写 Row 绕过生成器限制。

## 迁移稳定性

第十三条迁移给 `embedding_generations` 新增可空 `DOUBLE similarity_threshold`：null 表示按模型身份自动选择，0 显式关闭，非空数值由领域类型校验 0～1。先在隔离 MySQL 执行，再从完整 schema 生成并仅更新该 Entity（生成器因此移除包含浮点数模型的 Eq）。旧行不回填，不改 profile、连接密文或任务，应用读取时解释自动值。独立升级用例验证旧代际密文、连接修订、指纹保留及重复执行；阈值变更不重建向量。

第十二条迁移新增 `model_limits`，按请求模型名摘要保存最大并发与配置修订。已先在隔离 MySQL 执行，再反向生成 Entity；不修改向量代际、旧配置密文或日用量。已有模型没有该行时使用默认四并发，首次保存时显式持久化；只改并发与重建相互独立。

第十一条迁移新增 `model_usage_daily`，以 UTC 日期和模型名摘要为组合主键，原子累计请求、已知 Token、失败和未知用量次数；不保存逐请求记录。已先在隔离 MySQL 执行，再从真实表反向生成 Entity，不修改模型代际、空间或既有密文。所有模型调用入口复用这张表，汇总仅通过系统管理 Cookie 返回；口径见 [模型用量](模型设置与索引重建.md#模型-token-用量)。

第十条迁移新增 `instance_model_settings`、`embedding_generations`、`embedding_tasks`，分别保存实例管理空间及生效指针、模型代际与加密连接配置、按空间与记忆分隔的持久任务。已在隔离 MySQL 8.4 执行全部迁移，再使用相同生成选项反向生成这三张表的 Entity；不修改历史表或原密文。空库完整迁移、带数据的旧版本升级及重复执行均已验证；升级默认不启用模型，管理空间由初始化记录或显式开发配置绑定。代际、任务和根私钥的运行边界见 [模型设置](模型设置与索引重建.md)。

第九条迁移新增 `recall_runs`、`recall_items`，记录最终返回的记忆修订和可空评价，所有关联包含 `space_id`。迁移先在隔离 MySQL 执行，再以相同生成选项生成 Entity；没有手写第二套表模型。统计只从升级时开始，旧记忆、密文和接入凭据保持原值。升级使用 `up`，不自动删除历史统计；口径与验证见 [记忆召回统计与反馈](记忆召回统计与反馈.md)。

- 历史迁移需要的表、列标识与数据映射在迁移中固定，避免依赖随业务变化的当前 Entity，导致旧迁移无法重放。数据回填仍通过 SeaORM 执行；需要 Entity 时保留对应历史结构的 SeaORM Entity 快照。
- SeaORM 官方明确说明 MySQL 不支持整条 migration 的原子回滚。多条 DDL 中途失败时，必须检查实际结构和迁移记录，再进行有依据的恢复，不能假设什么都没有发生。[原子迁移说明](https://www.sea-ql.org/SeaORM/docs/migration/writing-migration/#atomic-migration)
- `fresh`、`refresh`、`reset` 不属于日常升级流程。涉及已有数据的回退或破坏性清理遵守项目授权约定；不可逆变更明确记录恢复办法。
- 发布时执行已审阅的迁移，不通过 Entity schema sync 在服务启动时自动改表。生产环境不参与 Entity 代码生成。

运行、CLI 安装与测试步骤见 [开发运行](开发运行.md)。真实远程数据库的 TLS 配置及生产升级 / 恢复演练仍需在部署阶段验证。

第三条迁移增加 `spaces.slug` 唯一列，为已有空间分配 `space-a` 等英文短标识，再设置非空和唯一索引。保留原主键、密码哈希、全部外键与索引 collection；对外标识变更不搬迁记忆。迁移可识别已创建的列与索引，已回填的标识不被重试覆盖。Entity 已在执行迁移后重新生成；看板和全部网络入口使用 slug。

第四条迁移新增 `secrets`，用 `(space_id, memory_id)` 关联记忆，保存密文格式、密钥编号、载荷修订、nonce 与可清空的密文。初次执行后发现 SeaQuery `.binary()` 实际落为 `BINARY(1)`，因此保留已执行历史，增加第五条迁移将密文列改为 `BLOB`；两条迁移均已执行，Entity 已从真实库重新生成。涉及删除密文表或缩窄列的回退主动拒绝，不能作为普通回退操作执行。

当前 CLI 对真实 `BLOB` 生成 `Option<Vec<u8>>`，但列注解为 `Binary(255)`；这是实测的生成元数据限制，不代表数据库只容纳 255 字节。保留生成结果，不手改 Entity，也不据此 schema sync。迁移中的 `BLOB` 是结构依据，真实 MySQL 已验证 60,000 字节原文加认证标签完整存取。再次生成须得到相同结果，并继续检查大载荷不截断。


第六条迁移创建接入和密钥表，并为来源事件、记忆头、修订和写回执增加可空的 `agent_id`。旧记录保持空来源；所有 Agent 外键均包含空间 ID。密钥列显式使用 BLOB；从真实 MySQL 反向生成后，BOOL 按生成器表示为 i8，业务层显式转换。新增关系使生成器不再推导原来未使用的 spaces／memory_sources 间接 Related，不保留另一套手工实体。新增两表和来源均由实际数据库生成。

第七条迁移只为 `secrets` 添加可空 JSON `contract` 列，空值表示旧记录的未知格式，不回填或解密历史内容。在隔离 MySQL 执行后，从真实库反向生成 `Option<Json>`；升级用例验证旧密文字节、nonce、载荷修订及密钥编号不变，重复执行不覆盖元数据。该列的删除回退明确拒绝，契约变更和遗忘使用现有 SeaORM 事务维护。

第八条迁移新增 `secret_access_audit`，包含空间与对象组合外键及可空 Agent 来源，仅保存取用元数据。已在隔离 MySQL 执行后使用上述生成命令加 `--tables secret_access_audit` 生成该表 Entity（不改其他既有 Entity）；无载荷或历史数据回填。新表删除回退明确拒绝，执行结果由业务层显式标记为客户端上报。

## embedding 批大小迁移

`m20261104_000014_embedding_batch` 为模型代际添加可空 `batch_size`。旧行保留 null 自动值，不改向量身份、连接修订或密文。先在独立 MySQL 8.4 执行迁移，再使用现有 SeaORM 2.0.4 CLI 反向生成 `embedding_generations` Entity；没有手写数据库行模型。

## 炼化与夺舍迁移

`m20261104_000015_soul_transfer` 添加 `transfer_receipts` 与 `memory_imports`，分别记录空间内包的处理回执和逐条迁入来源。先在隔离 MySQL 8.4 执行，再使用已批准的 SeaORM CLI 生成两张表的 Entity；旧记忆、密文及凭据不回填、不改写。包摘要采用实例根密钥派生的 MAC，不能用公开哈希离线猜测弱 Secret。导入与索引任务一次事务追加，详见 [炼化与夺舍](炼化与夺舍.md)。
