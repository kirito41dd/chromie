# 用户云端 Skill 托管与迭代

2026-11-19 修订。阶段一已在工作区实现，当前接口与存储行为见[云端 Skill 开发 Wiki](../../../wiki/云端Skill.md)。

## 产品定位

Chromie 是面向个人的云端记忆空间，已有记忆、召回和 Secret 等功能。本次新增的产品功能是**用户 Skill 托管**。用户在一个对话里沉淀的流程归属其空间，可由另一台设备、另一个 Agent 读取、使用和修订。

Chromie 随产品提供三样东西，它们服务于整个产品：

| Chromie 提供什么 | 职责 | 在 Skill 托管功能中的作用 |
| --- | --- | --- |
| 自带的使用 Skill | 由 Chromie 项目维护，教 Agent 何时以及怎样使用产品，包括记忆、召回和 Secret。 | 指导 Agent 发现已有流程、建议沉淀新流程、按用户纠正修订用过的版本。 |
| `chromie` CLI | 用户和 Agent 在本机使用的命令行工具，负责配对、接入、诊断及本机文件操作。 | 首版通过 CLI 拉取工作副本、校验文件、上传及修订完整包，也可回退历史版本。现有 `chromie skill export` 用于导出产品自带的使用 Skill。[CLI 接入](../../CLI接入实施.md) |
| Chromie MCP 服务 | 向 Agent 提供当前空间的资源和操作接口，按接入身份鉴权。 | 通过 Skills over MCP 提供发现与按需读取，通过 Chromie 工具接收使用报告。包的写入由 CLI 调用服务端发布接口。 |

例如，**“如何使用 Chromie”由项目随版本分发，“飞书项目缺陷验收”由用户保存在空间里**。修订后者，下一次任务即可从同一空间取得新版。[现有 Agent 接入与提示词分工](../../../wiki/Agent与提示词.md)

## 分两阶段交付

| 阶段 | 用户得到什么 | 谁来判断要改什么 |
| --- | --- | --- |
| 一 · 云端托管与对话内迭代 | 完整包的发布、发现、分文件读取、修订和回退。原生宿主连接空间 MCP 即可发现已发布的 Skill，Codex 可通过临时适配读取同一修订。 | 当前做事的 Agent 结合用户意图与本轮验证，在对话中建议沉淀或修订。服务端无需配置文本模型或 embedding。 |
| 二 · 后台自动维护 | 根据多次使用暴露的问题，识别值得修订或合并的流程。 | 等第一阶段积累真实使用结果，再设计触发条件、预算、证据和新版评测。第一阶段交付独立验收。 |

**日常场景。** 对话 A 跑通“飞书项目缺陷验收”，用户说“以后这样做”，Codex 通过 CLI 发布第 1 版。对话 B 只收到一个缺陷链接，也能找到流程。用户纠正“只有缺陷单需要复现条件”，Codex 拉取这份 Skill，改好后在普通需求和缺陷单上各验证一次，再通过 CLI 发布第 2 版。对话 C 用原来的入口读到新版。三次对话中用户都无需手动同步文件。

## 用户 Skill 的发布与读取

### 同事拿到目录就能用

托管单位是标准 Agent Skills 目录。根目录名与入口 `SKILL.md` 的 `name` 一致，包内引用使用相对路径。若作者附带参考文档、脚本、模板或许可证，发布和导出保留其路径及原始字节。符合首版大小和路径限制的社区 Skill 可以原样托管；从 Chromie 取出的目录也能直接交给支持本地 Skill 的宿主。包格式没有 Chromie 专属必填字段。[Agent Skills 格式](https://agentskills.io/specification)

**通用流程写进包，个人环境在运行时提供。** 写 Skill 时说明所需输入、用途和权限，例如“Grafana 地址和一个能查询日志的只读凭据”。使用者可以提供本机已配置的客户端、私有配置文件或自己的凭据管理器。装有 Chromie 的 Agent 还可以在当前空间查找相关记忆、按已有权限取用 Secret。缺少必要输入时，Agent 告诉使用者需要配置什么。具体记忆 ID、Secret 引用、作者机器路径及个人环境值留在各自空间的记忆或本地配置中。通用流程须有独立于作者空间的用法。

例如，把“按服务名和时间窗口查询错误日志”分享给同事。包里给出查询步骤、所需只读权限和结果格式。作者的 Agent 可以按本空间记忆定位数据源，同事则用自己已登录的 Grafana 客户端完成相同步骤。双方使用同一份文件，各自决定访问哪个环境。

**导出边界就是该修订的文件清单。** `chromie skill pull` 得到可直接分享的目录。CLI 将工作副本的来源、基础修订和重试记录保存在包目录之外。导出只复制清单内的文件，不追踪记忆和 Secret 引用，不附带空间数据、接入凭据或使用报告。作者写进文件的文字也会随包原样导出。接收者可直接本地使用，也可把这个目录发布进自己的空间，得到独立的 Skill ID 和修订历史。

### 云端发现与读取

空间内以稳定的 `skill_id` 标识一份 Skill，以单调递增的 `revision` 标识一次完整发布。这两个标识属于托管记录。

**标准读取协议。** 空间 MCP 端点声明 `io.modelcontextprotocol/skills` 与 Resources 能力。`skills/list` 分页列出已发布 Skill 当前版的完整清单，`skills/get` 按入口 URI 取清单，`resources/read` 按需读取其中的文件。清单给出各文件的 URI、原始字节长度和 SHA-256，包含入口文件本身。

**日常引用指向最新版。** 同一个 Skill 的入口在修订前后保持稳定，例如 `skill://chromie/<skill_id>/feishu-review/SKILL.md`。作为入口路径一部分的包名在首版创建时确定。客户端以 MCP 服务来源和入口 URI 识别 Skill，服务端按连接身份隔离空间。发布后，服务端从同一入口返回当前清单，原生宿主按协议缓存期限刷新。`skills/list` 与 `skills/get` 的每个 Skill 条目在 Chromie 命名空间的 `_meta` 中携带该清单的修订号，保持作者的 frontmatter 和文件字节不变。[Skills over MCP 清单字段](https://skills.extensions.modelcontextprotocol.io/specification/beta/skills#skill-entries)

**旧对话按需刷新。** 已经读完步骤的任务可以继续，无需后台轮询。如果宿主拿着旧清单读取一个刚被修改的脚本，就会发现摘要不同；文件已移除则读取失败。宿主丢弃未验证的内容，通过 `skills/get` 刷新清单，重新读取入口和接下来用到的文件，再继续任务。已完成的操作不用重做。[协议的读取校验](https://skills.extensions.modelcontextprotocol.io/specification/beta/skills#verification-on-read)

**Codex 的临时适配。** 产品自带的使用 Skill 指导 Agent 用 `list_skills(cursor?)` 分页枚举与原生一致的目录，按作者的名称和描述选择流程，再用 `read_skill(skill_id, path, expected_revision?)` 按需读取。默认读最新版，响应携带实际修订。接着读附件时带上刚才的修订号，如果已更新，工具返回“Skill 已更新”、当前修订和入口，不附文件正文。Agent 重读入口后继续。目录来自已发布的 YAML 元数据，可在未配置后端模型时使用。待 Codex 原生发现、读取和更新通过验收，即可移除这段适配指引；发布仍走 CLI。

**脚本在 Agent 本机执行。** 原生宿主按扩展规范管理针对该 Skill 的执行授权，范围也涵盖正文要求运行的命令。宿主若保存授权，须绑定清单中的 URI 和摘要，清单变化后按协议重新授权。Codex 过渡期由用户直接向 Codex 授权，Agent 在当前任务已有授权范围内调用本机工具，Chromie 无需再弹一次确认。服务器只提供文件；Secret 取用仍遵守当前接入权限。[协议的执行授权](https://skills.extensions.modelcontextprotocol.io/specification/beta/skills#security-considerations)

## 对话里如何沉淀和更新

- **发现。** 原生宿主根据服务发布的名称和适用说明选择 Skill。Codex 过渡期在现有 Chromie 使用 Skill 中补一条发现规则：用户交办可能已有惯例的任务时列出目录、按描述选择，复用本对话已见条目，普通问答直接回答。hook 继续负责原始消息采集。
- **选择。** 用户明确表示“以后照这个做”，Agent 优先修订这次用过的 Skill，其次寻找同类流程，最后才新建。如果只完成了一项可能值得复用的复杂任务，Agent 可以在交付结果后提出一次具体建议，说明能省掉哪几步，用户同意后再发布。一次偶发的环境故障只记录其适用条件和观察结果。
- **发布和修订。** 拟在客户端提供 `chromie skill validate`、`pull`、`push` 和 `rollback`。新建从本地包目录开始；修订时用 `pull` 取得完整可编辑副本，并记录空间、Skill ID 和基础修订。拉取完成时须保证所有文件属于同一版。副本放在任务工作目录。Agent 修改文件、验证行为，再用同一个 `push` 创建或修订。变更脚本或关键判断步骤时在隔离样例上验证，缺乏验证时保留工作副本并说明。首版复用同一条 CLI 写入路径，无需另建一组 MCP 写包工具。
- **文件怎样上传。** `validate` 可离线列出将发布的文件并检查入口、路径和大小，`push` 自动执行相同检查。CLI 使用已有的 Agent 接入凭据向 Chromie HTTP 接口上传文件字节，并提交整个包的路径和摘要清单。CLI 仅从包根目录收集文件，并排除版本控制目录。服务端独立核验身份、清单与收到的字节，再一次发布完整版本。删除文件体现为它从新版清单中移除。二进制模板由 CLI 直接传输，模型只需知道文件路径和发布结果。
- **留据与回退。** 记录来源 Agent、基础修订、变更原因及可提供的公开验证摘要。使用报告可幂等提交，区分“实际使用”“执行端报告已验证”“用户明确纠正”。原生宿主若能带回使用时的修订号，或 Codex 从读取响应取得该号，报告就计入该版。宿主只提供稳定入口时，记录为“版本未知”，只计入该 Skill 总量。只有读取记录时，使用结果保持未知。回退以当前修订为基础重新发布某个保留版本的清单，生成一个新版本号。

创建、修订和回退均带 `request_id`，修订和回退还带 `expected_revision`。CLI 在首次发送前持久化请求 ID、操作目标、基础修订和规范化清单摘要（回退时记录目标修订），绑定当前实例、空间与工作副本。终端中断后原样重试复用同一 ID。服务端完成鉴权后优先重放相同请求的回执，同一 ID 对应不同请求则报冲突。CLI 取得回执后才更新工作副本的基础修订并清除待确认记录。若文件在断线后又被编辑，CLI 可凭原请求 ID 向服务端核对前次操作结果，再为新改动生成新请求。两个 Agent 同时修订时，冲突方保留本地改动，读取新版并核对差异后再决定是否重提。空间与作者身份取自服务端验证过的 Agent 接入，hook 上传密钥不能读取或发布 Skill。[现有身份与幂等约定](../../MCP接口设计.md)

## 存储决策：首版使用 RustFS

RustFS 与现有 MySQL 一起随 Compose 部署。RustFS 保存文件的原始字节，包括 `SKILL.md`、参考文档、脚本和二进制模板。MySQL 8.4 保存空间归属、当前修订、清单和使用记录，继续负责决定一个版本何时可见。搜索和列目录只读 MySQL，读取文件时 Chromie 先校验接入身份及对应空间的修订清单，再从私有桶取内容。MCP、CLI 和浏览器只接触 Chromie 接口。[RustFS 官方仓库](https://github.com/rustfs/rustfs)

**给未来的附件留什么。** 同一空间内，相同字节可以同时供多个修订、多个 Skill 使用。对象标识、空间隔离、摘要校验和按引用回收独立于 Skill；以后记忆附件可用自己的业务表引用同一个对象。文件名、用途、所属记忆及访问授权属于具体业务引用。阶段一只开放 Skill 包已有的文件入口，通用附件上传、预览、配额和炼化包的附件迁移留给附件专项设计。

| 拟建表 | 责任与主要约束 |
| --- | --- |
| `skills`、`skill_revisions` | 空间内唯一包名、稳定 ID 和当前修订；每版记录基础修订、frontmatter、来源 Agent、原因及验证摘要。写入回执遵守既有幂等规则。 |
| `skill_revision_files` | 用空间、Skill、修订和相对路径定位文件，引用同空间的对象，保存展示所需的媒体类型。同一修订内路径唯一。 |
| `stored_objects` | 记录空间、不可变对象 ID、RustFS 内部键、SHA-256、原始字节数与生命周期状态。相同空间和摘要只选用一个可引用对象；物理键由服务端生成，独立于文件名。跨空间不共用对象。 |
| `skill_usage_reports` | 每次报告绑定空间、Skill 与已鉴权的 Agent。能确定版本时绑定所属修订；版本未知时修订列留空，保留结果及必要的公开依据。 |

### 发布与回收

1. **上传。** 先校验清单、路径和大小。服务为新字节登记有期限的待发布对象，用唯一物理键在数据库事务外上传，核对实际内容的 SHA-256 与字节数，再允许进入发布步骤。复用已验证对象时从当前空间查找。传输超时可重试，未知结果按摘要核对；S3 ETag 不能充当内容 SHA-256。
2. **发布。** 在短 MySQL 事务里核对幂等回执并锁定本次对象记录，验证对象在本空间可引用。新建受空间内包名唯一约束；修订和回退以空间、Skill ID 和 `current_revision = expected_revision` 为条件更新 `skills`。只允许更新一行，未命中则回滚并返回修订冲突。新清单、当前修订及回执一起提交。即使两个 Agent 修改完全不同的文件，也只有一个能从同一版发布成功。并发上传相同字节时选用已有对象，其他副本留待回收。对象写完、事务提交前宕机时读者仍看到旧版；提交后响应丢失时返回原回执。
3. **保留与回收。** 保留当前及最近四个旧版的完整清单，刚被替换的版本至少保留 24 小时。清理器在事务内锁定对象、确认没有保留的业务引用和有效上传租约，才标为待删除。发布操作不得重新引用待删除对象。事务外按该对象唯一物理键删除，失败继续重试；相同内容以后重新上传也使用新物理键。定期核对逾期上传与桶中无登记的对象，覆盖进程崩溃和迟到写入。修订元数据可长期保留，修订历史标明仍可回退的版本。详细使用报告按空间保留最近 100 条且最长 30 天，更早报告只保留计数，按 Skill 和已知修订汇总，版本未知的单列。

包的互通上限为每版 **512 个文件、合计 16 MiB 原始内容**，包含 `SKILL.md`。发布仅接受包内普通文件，拒绝绝对路径、目录穿越、符号链接、重复或跨平台落盘冲突的路径。客户端下载或重用缓存时校验实际字节。对象缺失、内容损坏或 RustFS 暂不可达时，文件读取或发布应明确报错，保留原清单与修订；普通记忆和 Secret 沿用各自的存取路径。表结构继续按 SeaORM schema-first 流程实施。[扩展规范中的上限](https://skills.extensions.modelcontextprotocol.io/specification/beta/skills#limits) · [数据库开发流程](../../数据库开发流程.md)

### 零配置部署与恢复

- 发行与源码 Compose 默认启动固定版本的 RustFS，数据挂载到宿主机 `data/rustfs/`，实例凭据保存在权限受限的 `config/` 下。对象服务和控制台仅在 Compose 私网可达。初始化按“准备配置 → RustFS 就绪 → 创建私有桶和应用凭据”幂等执行；应用凭据仅用于该实例所需的桶操作。用户仍只准备 config 与 data 两个目录。正式发版验证 Linux amd64、arm64 镜像与卷权限。[RustFS Docker 文档](https://docs.rustfs.com/en/installation/container/docker)
- 从已有 Chromie 升级时，仅首次为新增对象存储生成配置。初次配置须先持久化凭据，再建桶，通过后记录初始化完成；首次中断用同一凭据续做。已有完成标记、用户对象或数据库引用时，缺少对应凭据或桶须报告并恢复配套备份。重启和升级沿用原空间、记忆、Secret、根私钥和接入。
- 首版沿用停服冷备，将原配置、实例根私钥、MySQL、RustFS 数据目录及原有数据作为同一组备份。恢复后按保留清单检查对象存在性、字节数和摘要，并在隔离实例读回代表性 Skill 及既有记忆。仅持有 MySQL 导出时可恢复目录信息，无法还原文件原文；RustFS 暂时离线时暂停对象回收。实施时同步更新部署与恢复手册。[现有部署与备份约定](../../Docker部署.md)

## 阶段一验收

1. **托管功能的原生读取与日常使用（主验收）。** 用真实 SEP-2640 宿主分别验收协议互通与日常组合。仅配置端点时，验证分页枚举、按 URI 取清单及按需读取文本和二进制模板。再在同一宿主加载 Chromie 使用 Skill 并接入 CLI：原生发现一份测试流程，按其公开契约通过 CLI 在本地使用虚构凭据，随后由使用 Skill 引导 Agent 把用户纠正提交到同一云端 Skill。新会话须能发现新版并验证摘要。记录宿主版本与实际调用。
2. **Codex 过渡适配。** 在隔离空间用三个全新 Codex 对话完成上述飞书场景。B、C 不点名 Chromie，仍能找到并使用正确版本。核对其内容与原生宿主所读完全一致，加一条普通问答检查是否无谓查库。
3. **修订可见性。** A 已读第 1 版入口，B 修改脚本、删除旧模板并发布第 2 版。新对话从原入口发现第 2 版；让 A 继续读附件，分别验证原生宿主刷新清单、Codex 收到修订过期后重读入口。实测原生宿主能否将当时的修订号带回反馈工具：带回第 1 版则计第 1 版，缺失则计版本未知，两者都不会增加第 2 版的统计。让两台 CLI 从同一版并发改不同文件，只允许一个成功，冲突方应保留本地编辑。
4. **文件与失败恢复。** 用 CLI 发布同时含中文文档、脚本和二进制模板的目录，在另一设备拉取后逐文件对比。修改文本后再次发布，核对未改模板的摘要。分别在上传中、对象已校验但 MySQL 尚未提交、MySQL 已提交但尚未返回回执时注入中断。最后一种须退出 CLI，再从同一工作副本重试，应拿到原回执、更新本地基础修订且只产生一次发布。覆盖并发上传相同内容、过期上传与回收竞争及回退。清理旧修订后，其他保留清单仍能读出共享文件。
5. **部署与备份。** 从两个空目录启动，再从带既有记忆和 Secret 的测试实例升级，验证自动建桶、重启后凭据稳定及旧数据可用。用同一组冷备在隔离实例恢复，逐文件校验；断开 RustFS 或模拟缺失对象时，检查错误提示、原修订和普通记忆可用性。
6. **边界与降级。** 两个空间使用同名 Skill、上传相同字节仍完全隔离；hook 密钥不能取包，客户端不能凭对象 ID 绕过清单鉴权。拒绝越界路径、损坏摘要和超限包。关闭文本模型与 embedding 后重跑发现、发布和读取。用无副作用的本地脚本验证原生宿主的授权及清单变化后的重新授权；在 Codex 过渡路径验证已授权任务可直接执行，服务端始终只交付文件。
7. **像社区 Skill 一样分享。** 准备一份含脚本、模板和许可证的标准测试 Skill，由作者在有虚构记忆及 Secret 的空间原样托管、拉取。比对导出目录与输入目录的相对路径及逐文件摘要。把导出目录交给另一台未安装 Chromie、也无法访问作者实例的宿主，接收者只提供自己的测试服务地址和只读凭据，应能完成同一查询。再将目录发布到另一个空间，验证取得独立身份，修订副本不影响作者版本，双方均未获得对方的记忆或 Secret。
