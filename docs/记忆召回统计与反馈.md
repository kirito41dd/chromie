# 记忆召回统计与反馈

2026-11-03，按用户确认的口径实现。目标是观察热点与 Agent 认为有帮助的记忆，首版不改变检索排序，不要求用户逐条评价。

## 统计口径

- **Agent 召回次数**：一次 MCP 召回的最终 JSON 中包含该记忆就记录一次；只进入候选、被过滤或被预算删除的条目不计。它表示服务端返回，不保证 Agent 已阅读。每次调用产生独立 `recall_id`；重新调用是一次新的召回。
- **已评价次数**：Agent 明确判断过的条目数；包含有帮助和没有帮助。未反馈保持未知。
- **标记有用次数**：已评价条目中，Agent 认为对本次任务有帮助的次数，不等于经过服务端验证的任务成功。
- **Web 调试次数**：单独记录，不混入 Agent 的热度与评价。直接服务管理调用另标记为 internal。

同次召回的同条记忆最多记一次。反馈绑定当时返回的修订；召回次数可跨修订累计，已评价和有用次数展示当前修订，避免旧内容的评价直接归给更正后的内容。统计从升级开始，不推算历史。

## Agent 流程

1. `recall` 返回 `recall_id` 和原有记忆结果。
2. Agent 结合当前任务判断，使用新增的 `feedback_recall` 批量提交多次召回的评价；每批包含 `recall_id`、`evaluated_memory_ids` 和其子集 `useful_memory_ids`。
3. 同一条目相同评价重放不增计；矛盾评价返回冲突，整批不部分写入。尚未评价的条目可以后补。无法判断就不报，不强行补负面评价。

服务端只允许同空间、原召回 Agent 回报实际返回的 ID；Agent 身份来自 Bearer 鉴权，不接受自报来源。Web/internal 记录不能经此工具评价。遗忘后的记忆不能继续评价。一次最多 20 次召回，每次最多 10 条，拒绝重复 ID、越界集合和不属于召回的条目。

MCP 指引在任务告一段落时引导 Agent 合并反馈，不为了反馈额外召回，也不把记忆正文或敏感原文填进评价。反馈失败不影响回答与正常操作。

## 数据与边界

新增 `recall_runs` 和 `recall_items`，通过 SeaORM migration 建表、在隔离 MySQL 执行后反向生成 Entity。所有引用包含空间 ID，条目关联准确的记忆修订；只存 ID、渠道、鉴权 Agent、时间和可空评价，不复制查询、记忆正文、凭据或 Secret 原文。

召回经过筛选和预算后再事务性记录；统计失败保留召回结果，返回空 `recall_id` 并标明统计不可用，只记录不含正文的错误类别。评价在空间锁事务中校验并写入，重复、冲突、并发及权限变化遵守相同规则。

Web 提供最近、近 30 天热门、近 30 天有用三个视图：热门按 Agent 返回次数，有用按当前修订的正面反馈次数；无记录时明确展示空状态。卡片展示 Agent 召回、当前修订有用/已评价，Web 调试数在调试结果中独立显示。召回统计放在 Web 的 `debug.hits[].usage`，与原有诊断一起位于正文预算之外，不改变最终结果集；MCP 不携带这些统计字段。有用率只以已评价为分母，同时保留样本数。

## 验证范围

验证全新建库及旧库升级、反向生成稳定性；最终预算结果计数、渠道分离、零结果、同次去重；反馈重放、冲突整批回滚、越空间/Agent、未返回 ID、禁用接入、修订变更和遗忘；近 30 天边界和列表排序。使用真实隔离 MySQL/Qdrant、MCP HTTP 联调及虚构空间浏览器验收，不使用真实敏感资料。
