# Secret 加密与密钥持久化

更新于 2026-10-28。用户已确认使用 `hkdf` 与 `aes-gcm`，复用现有持久化 P-256 私钥；不采用此前的 HPKE／JWE 候选，不引入 OpenSSL。

| 依赖 | 用途 |
| --- | --- |
| `hkdf` 0.13.0 | 从解析后的私钥字节，经 HKDF-SHA256 派生带用途、空间及对象上下文的密钥 |
| `aes-gcm` 0.11.1 | 使用 AES-256-GCM 对 Secret 进行认证加密 |
| 原有 `p256`、`sha2` | 读取 P-256 私钥、计算公开密钥编号及 SHA-256 |

依据：[HKDF 规范](https://www.rfc-editor.org/rfc/rfc5869.html)、[GCM 规范](https://csrc.nist.gov/pubs/sp/800/38/d/final)、[hkdf](https://docs.rs/hkdf/latest/hkdf/)、[aes-gcm](https://docs.rs/aes-gcm/latest/aes_gcm/)。

## 只有一份必须保管的根私钥

**实例根私钥不能扔，不能因重启、部署、清理目录或修复登录问题而删除、重生成或直接替换。丢失后，历史 Secret 无法从数据库恢复。**

`CHROMIE_KEY_FILE` 指定同一份 PKCS#8 P-256 私钥，默认 `.local/chromie-key.pem`，文件权限须为 `0600` 或更严格。JWT 使用该私钥做 ES256 签名，Secret 使用其解析后的固定字节作为派生根材料。不会把 PEM 文本直接 hash 成密钥，换行格式变化不应改变解密结果。

派生的 AES 密钥不单独落盘。加载原私钥，再使用相同上下文即可重新派生；数据库里的 `key_id` 是规范化公钥的 SHA-256 编号，不是 AES 密钥或私钥。

生产部署应把私钥放在受控的持久目录，通过配置指定绝对路径；不能只留在临时容器文件系统或可清理的 checkout `.local` 中。数据库与私钥分别做受保护的备份，不提交 Git，不粘贴到聊天，不把唯一备份再存进依赖它解密的 Secret 系统里。

恢复数据库备份时，也要恢复对应私钥。服务启动会核对现存密文的密钥编号；缺失或不匹配时拒绝启用，不自动创建新钥覆盖。`init-key` 仅供首次初始化新实例，不能用它修复已有实例的私钥丢失。

## 密文格式与绑定

- 当前格式版本为 `1`，使用 HKDF-SHA256、256 位 AES 密钥、96 位随机 nonce 和 128 位 GCM 标签；标签附在密文末尾。
- 派生上下文与附加认证数据绑定用途、空间内部 ID、Secret 记忆 ID 和载荷修订。每次更新产生新载荷修订并生成新 nonce，跨空间、对象或载荷修订调换不能解密。
- 载荷修订与记忆说明修订分开保存。修改公开说明不会改变原文的解密上下文；HTTP PUT 更新原文时，两种修订按各自规则前进。
- 幂等回执使用另一用途域派生的 HMAC-SHA256 摘要，不保存 Secret 原文的裸哈希，避免数据库副本成为弱密码离线猜测材料。
- 存储保留格式版本、密钥编号、载荷修订、nonce 和密文；原文不进入记忆正文、原始消息、索引、任务、回执或日志。

更换空间密码不需要重新加密 Secret；后续请求使用新密码。当前不提供自动根私钥轮换，换钥必须保留旧钥并显式迁移全部历史密文，同时考虑旧数据库备份与 Web 登录失效。

具体接口、curl 操作及恢复步骤见 [Secret 记忆](Secret记忆.md)；开发验证方法见 [开发运行](开发运行.md)。
