# 开发运行

面向贡献者的本机构建与验证。只想使用服务时，先看 [Docker 部署](Docker部署.md)。以下从仓库根目录执行；本地配置、数据、私钥和验收产物不提交。

## 准备开发数据库

使用支持 Rust 2024 的工具链、Docker Compose 和 Python 3。完整镜像固定使用 Rust 1.99.1；依赖版本由 Cargo.lock 固定。Nushell 用于验证项目文档中的 Nu 示例，Node 仅用于浏览器桥接测试，不是前端运行依赖。

首次准备配置，已有文件与根私钥必须保留。以下命令在 Bash 与 Nushell 中相同：

```shell
cp .env.example .dev.env
chmod 600 .dev.env
```

在自己的编辑器中填写数据库密码、DATABASE_URL 和 Qdrant API Key；URL 中的特殊字符需要编码。文件是可信的 Shell 配置，包含空格等字符的值须正确引用。

Bash：

```bash
set -a
source .dev.env
set +a
docker compose -f compose.dev.yaml --env-file .dev.env up -d
cargo build --locked -p chromie --bin chromie-server
./target/debug/chromie-server migrate
```

Nushell：

```nu
source scripts/load-dev-env.nu
^docker compose -f compose.dev.yaml --env-file .dev.env up -d
^cargo build --locked -p chromie --bin chromie-server
^./target/debug/chromie-server migrate
```

开发 Compose 只启动 MySQL 8.4 与 Qdrant，宿主端口分别为 13306、16333（REST）和 16334（gRPC）。不要与完整部署 Compose 的数据目录或项目名混用。停止容器不删除原数据卷。

## 首次启动服务

仅对全新实例生成根私钥。已有实例必须使用原私钥；缺失时恢复备份，禁止重新初始化。以下命令在 Bash 与 Nushell 中相同：

```shell
./target/debug/chromie-server init-key .local/chromie-key.pem
```

CHROMIE_KEY_FILE 默认指向该文件。它同时用于 JWT、Secret 与接入密钥加密，必须持久保存并与数据库分别安全备份，Unix 权限为 0600。

创建空间时通过隐藏输入提供密码，不写入命令参数。

Bash：

```bash
python3 -c 'import getpass; print(getpass.getpass("空间密码："))' \
  | ./target/debug/chromie-server create-space work 工作
```

Nushell：

```nu
^python3 -c "import getpass; print(getpass.getpass(\"空间密码：\"))" | ^./target/debug/chromie-server create-space work "工作"
```

空间标识为 1～32 个小写英文字母与单个连字符，不能以连字符开头或结尾；密码为 12～1024 字节，不含控制字符。展示名称可用中文。

以下命令在 Bash 与 Nushell 中相同：

```shell
./target/debug/chromie-server serve
```

默认监听 127.0.0.1:8732。/health 检查进程存活，/ready 检查数据库与索引连通。新增空间或改名后重启服务注册路由；改密无需重启，旧 Web 登录态失效。HTTP 与 HTTPS 均可使用，远程 Origin 及 TLS 见 [Docker 部署](Docker部署.md)。

## 前端开发

首次安装已确认的工具，以下命令在 Bash 与 Nushell 中相同：

```shell
rustup target add wasm32-unknown-unknown
cargo install wasm-pack --version 0.15.0 --locked --root .local/tools
./scripts/build-web.sh
```

页面在 `web/ui/`，Rust 状态与桥接在 `web/src/`，浏览器桥接在 `web/bootstrap.js`。产物写入被忽略的 web/pkg，服务默认从此目录读取；CHROMIE_WEB_DIR 可指定其他产物目录。

- 修改 Slint 或前端 Rust：重新构建 Web，刷新页面。
- 修改 bootstrap.js 或 index.html：它们被嵌入服务二进制，需要重编译并重启后端。
- 公共 Wasm／JS 资源按 ETag 重验证；浏览器开发者工具启用 Disable cache 会绕过缓存。
- 中文字体随 Wasm 打包，不访问外部字体服务。完整字体较大，首次加载成本和缩放阶段的 GPU 闪烁是已知体验边界。

打开 [本地入口](http://127.0.0.1:8732/)，使用自己创建的空间。Web 提供看板、接入、采集消息、召回调试、炼化／夺舍；初始管理空间可访问实例模型设置。

## 客户端与插件构建

发布客户端与服务端使用独立 feature，避免将后端依赖编入用户 CLI。以下命令在 Bash 与 Nushell 中相同：

```shell
cargo build --locked --release -p chromie --no-default-features --features client --bin chromie
cargo build --locked --release -p chromie --no-default-features --features server --bin chromie-server
python3 scripts/build-cli.py --binary target/release/chromie
python3 scripts/build-codex-plugin.py --binary target/release/chromie
```

CLI 产物位于 web/pkg/cli，插件和通用兼容包也写入 web/pkg。安装器只能下载已构建的对应平台程序；跨平台必须实际构建，不可仅更改 target 标签。额外平台产物打包到镜像的方式见 [Docker 部署](Docker部署.md)。

日常接入使用 Web 页面的安装与 init 命令，不手写密码上传器；MCP 与 hook 使用每 Agent 独立密钥。Codex 安装后在 /hooks 信任，必要时完全退出并重启桌面应用。完整流程见 [Codex 接入](Codex接入与使用.md) 与 [通用接入](通用接入.md)。

## 数据库与维护

统一采用 SeaORM schema-first，迁移及 Entity 生成见 [数据库开发流程](数据库开发流程.md)。不删除或重写已发布迁移，不对已有实例回退数据库。

以下命令在 Bash 与 Nushell 中相同：

```shell
./target/debug/chromie-server rename-space work work-notes
./target/debug/chromie-server rebuild work-notes
./target/debug/chromie-server --help
```

改名后更新接入并重启；旧队列不自动改投。rebuild 从 MySQL 重新登记索引任务，需要正在运行的服务消费。密码更新仍通过标准输入，详见命令帮助。

## 验证

正式代码的 lint 范围仅为 bin/lib，不把测试、示例与基准纳入基础 lint 限制。以下命令在 Bash 与 Nushell 中相同：

```shell
cargo fmt --all --check
cargo check --locked --workspace --lib --bins
cargo clippy --locked --workspace --lib --bins
cargo clippy --locked -p chromie-web --lib --target wasm32-unknown-unknown
cargo test --locked --workspace --lib
node --test web/tests/bootstrap.test.mjs
python3 scripts/test-shell-examples.py
```

桥接测试使用模拟浏览器时钟与网络，不代替真实浏览器的视觉、Cookie、输入法与交互验收。Shell 检查只解析片段，不执行服务、密码或建库命令。

真实服务测试默认 ignored，显式执行前准备单独的测试库与权限，将连接保存在本地 .dev.env；数据库名必须以 _test 结尾。仅使用虚构资料和测试根私钥，不读取、替换开发或生产实例根私钥。

| 变量 | 用途 |
| --- | --- |
| CHROMIE_TEST_DATABASE_URL | 常规服务集成测试 |
| CHROMIE_MIGRATION_TEST_DATABASE_URL | 迁移测试；必须为一次性空库 |
| CHROMIE_TRANSFER_TARGET_DATABASE_URL | 跨实例迁移目标测试库；与常规测试库不同 |

测试复用开发 Qdrant 地址及 API Key，索引按测试空间隔离。先按前面的 Bash 或 Nu 方式加载环境，再运行需要覆盖的用例。以下命令在 Bash 与 Nushell 中相同：

```shell
cargo test --test workflow -- --ignored --test-threads=1
cargo test --test web_login -- --ignored --test-threads=1
cargo test --test transfer -- --ignored --test-threads=1
cargo test --test migration -- --ignored --test-threads=1
```

迁移包使用正式 age KDF，在未优化构建中较慢，可按需使用 release 测试；不要降低产品参数来加速验收。Codex 集成测试需要已安装的 codex，使用临时 CODEX_HOME，不修改真实用户配置。

安装器验证用 `python3 scripts/test-cli-installer.py`；独立镜像验收用 `python3 scripts/test-docker-deployment.py`。后者需要先构建镜像，使用独立 Compose 项目与虚构配置，不能传入生产目录。测试日志、截图与本机运维记录放在 .local，不进入仓库。

Linux 上 Docker 生成的配置属于 root，镜像验收需要以 root 读取、备份和恢复这组虚构文件；不要放宽产品配置的目录或文件权限。以下命令在 Bash 与 Nushell 中相同，`chromie:ci` 为已构建并载入本机 Docker 的验收镜像：

```shell
sudo python3 scripts/test-docker-deployment.py --image chromie:ci --client-container
```

CI 只将 `results.json` 的无凭据统计复制到 runner 可读目录再上传，私有配置和命令日志留在隔离目录内。

## 发布

Docker 和插件包携带项目与特别组件许可。对外提供二进制或 Wasm 时，应同时提供对应版本的可构建源码和所需第三方许可，见 [第三方许可说明](../THIRD_PARTY_NOTICES.md)。生产更新前备份原配置、数据库及原根私钥，检查升级后数据和接入；不要在真实空间写入验收夹具。
