# Secret 格式与用途契约

2026-10-30，用户已批准，服务端与 CLI 已实现并部署本机。本文保留契约及兼容约定。

## 目标

Agent 无需读取原文，就能知道 Secret 的编码、字段位置和字段用途，再由本地程序解析、使用。公开说明继续负责召回，结构化契约负责解析；两者独立保存。

数字组成的密码仍是文本，例如 `001234` 的前导零必须保留。不能通过“能否解析成 JSON”猜测原始类型，也不能从字段名自行确定认证方式。

## 最小数据模型

在 `secrets` 增加可空 JSON 列 `contract`。空值映射为 `unknown`，供旧记录兼容；现有 `format_version` 是加密封包版本，不能复用为载荷类型。契约自己的 `version` 用于其结构演进。

| 格式 | 描述内容 | 本地处理 |
| --- | --- | --- |
| `text` | 整段文本的用途，如 `password` 或 `api_token` | 按 UTF-8 原样读取，不做数字转换或自动去空白 |
| `json` | 声明需要的字段路径、值类型和用途 | 按明确路径取值并校验类型 |
| `binary` | 不透明二进制文件 | 直接交给明确需要该文件的本地程序 |
| `unknown` | 旧记录或旧客户端未提供描述 | 可以保留和导出，自动使用前先补齐契约 |

文本密码示例，仅含公开描述：

```json
{
  "version": 1,
  "format": "text",
  "kind": "password"
}
```

虚构 JSON 凭据包示例，不代表现存 Grafana 记录的实际结构：

```json
{
  "version": 1,
  "format": "json",
  "fields": {
    "username": { "pointer": "/auth/user", "type": "string" },
    "password": { "pointer": "/auth/pass", "type": "string" },
    "service_url": { "pointer": "/server", "type": "string" }
  }
}
```

`fields` 的键表达用途，`pointer` 定位实际字段；字段路径使用现有 `serde_json::Value::pointer` 支持的语法。第一版只检查明确声明的字段存在且类型匹配，允许原 JSON 有其他字段。契约不包含值、默认凭据、可执行脚本或自动执行的网络目标。

建议契约上限 4 KiB、最多 16 个字段；路径和用途名称也设长度限制。完整契约只在 `get_memory` 当前视图按需返回，召回列表仅显示格式摘要。返回预算不足时明确报错或要求更大预算，不能截断路径或返回半份契约。历史记忆修订不冒充历史载荷契约。

## 格式与使用方式的边界

契约说明“哪一段是密码、哪个字段是 Token”，具体任务与目标服务接口说明决定如何使用，例如输入登录表单、调用登录接口或放入某个认证头。`api_token` 不自动等同于固定的 Bearer 用法。

字段路径和用途只记录用户明确提供、已知模板约定或经确认的结构。结构校验只能证明字段存在和类型匹配，不能证明一个字段在业务上一定是密码。JSON 中的键本身也可能敏感，不默认将任意 JSON 的全部键展开后发给模型。

## 录入

1. 用户说要保存 QQ 密码时，Agent 给出的隐藏输入命令声明 `text / password`；用户仍只输入密码。保存 API Key 时，Agent 根据明确用途声明 `text / api_token`。
2. 保存 JSON 文件时，Agent 可以先准备只含公开结构的契约文件，用户或本地 CLI 提供原始凭据文件。客户端和服务端都验证实际格式及声明字段，错误只报告格式或所需路径，不带值、原文片段或解析器上下文。
3. 新载荷及其契约在同一事务中保存，写操作的幂等摘要包含契约。新客户端明确声明格式；旧客户端省略时保持 `unknown`，兼容原始字节存取。
4. 后续替换原文若不提供新契约，服务端用既有契约验证新载荷，匹配才保留；不能静默留下不匹配的旧契约。原契约未知时继续保持未知。

## 召回与取用

1. `recall` 定位 Secret，`get_memory` 读取公开契约与当前记忆 `revision`。
2. Agent 根据契约准备本地解析程序。程序取用时带上该修订作为预期版本；服务端在当前事务中校验修订再返回原文。版本变化时拒绝取用，保留本地旧文件，Agent 重新读取契约后处理。
3. 复用现有记忆修订：原文、契约或公开说明变化都会推进修订。这样即使只有说明变化导致一次重新读取，也能保证实现简单、契约与载荷一致；加密内部的 `payload_revision` 继续保持原有用途。
4. 本地程序校验编码、路径和类型后使用原文。失败时只返回安全的结构错误，不把原文、JSON 值或认证请求输出给模型。

现有原始下载入口继续兼容旧客户端。Agent 依赖契约进行自动解析时必须使用带预期修订的取用方式，不能先取一份契约、随后无条件下载任意新版本原文。

## 补齐旧记录

旧记录不自动解密扫描、改写或猜测格式。用户已明确 QQ 保存的是原始文本密码，可以直接提出对应的文本契约；Grafana 保存的是 JSON，但具体路径与用途仍需确定。

补契约沿用 Secret 的独立 HTTP 权限入口，不通过普通 `correct_memory` 随意改写：CLI 提交公开契约和预期修订，服务端在内部校验现有原文与契约是否相符。成功后只更新契约并推进记忆修订，不改密文、nonce、引用或原文，也不更换根私钥。

不知道旧 JSON 结构时，可提供显式调用的本地结构检查：只在本机生成不含值的结构清单，先由用户选择允许公开的字段，再形成契约。它不自动上传全部字段名；字段用途仍由明确约定确认。此过程只需在旧记录首次使用前完成。

## 存储、权限与遗忘

- 继续采用 schema-first：新增 SeaORM migration，在隔离 MySQL 执行，再反向生成 Entity；不手工修改生成模型。
- MCP 返回的契约属于允许模型读取的元数据，继续遵守空间边界。原文读写和契约变更仍要求对应 Agent 的 Secret 权限；契约本身不授予权限。
- 普通 `correct_memory` 只维护公开说明与范围；契约单独校验，避免一句说明更正让解析约定失真。
- 契约变更与修订追加同事务提交。遗忘 Secret 时同时清除契约，不能留下字段结构信息。
- 现有密文、根私钥、加密封包版本和用户数据保留；仅添加可空元数据列。格式与用途描述不交给 LLM 推断原文。

## 实现顺序与验收

1. 定义契约类型与校验器，使用现有 Serde／serde_json；校验错误只携带稳定代码和安全说明。
2. 添加迁移并生成 Entity，覆盖已有密文升级为未知契约、空库迁移及大载荷不变。
3. 接入原文上传与替换、公开元数据读取、带预期修订的下载，以及旧记录契约补齐入口。
4. CLI 接入隐藏文本输入、JSON 文件与公开契约；更新 Agent 指南，明确未知格式与版本冲突的处理。
5. 验证文本前导零保留、JSON 嵌套字段、错误类型、更新后不匹配、跨空间与权限拒绝、并发版本变化、幂等重放、遗忘清理，以及旧密文不变。
6. 使用虚构数据进行实际对话验收：模型只接触契约，本地程序能按约定使用；不能仅以 HTTP／MCP 握手通过替代该验收。

第一版复用现有依赖；重要依赖若出现新增需求，仍先向用户确认。接口测试与自然对话验收分别记录，不能仅凭其中一项推定另一项通过。
