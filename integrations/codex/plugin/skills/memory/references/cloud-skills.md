# 使用和维护用户托管的 Skill

原生宿主通过 Skills over MCP 发现流程。兼容宿主用 `list_skills({})` 取得作者写在 YAML 中的名称、适用说明以及 Skill 标识和修订。本页不足以决定时，把 `next_cursor` 原样作为下一次的 `cursor`。选中后，用 `read_skill` 携带 `skill_id` 和 `expected_revision` 读取入口；遇到具体步骤再带同一修订和相对路径读附件。

同一服务和空间内复用本对话已经看到的目录。切换接入、发布新包或得知目录变化时重新列出。收到 `revision_conflict` 时，按该 ID 重读当前入口，更新对这项流程的认识后继续任务。脚本在本机按用户和宿主授权执行。

首次沉淀时，先查空间里有没有适用的流程。重复使用、换人接手是提出建议的时机。用户同意把流程存入共用库，就验证并发布。个人偏好写入记忆，一次性的任务交付结果即可。

修订从实际用过的版本开始。用 CLI 拉取到独立任务目录，记录原修订号。根据用户确认的业务规则，准备一个能体现改动的样例和一个应保持原结果的样例，先写下各自的预期。规则有生效范围时，两侧各选一个样例，按业务所属期间判断，注意跨期补录。包里有脚本就实际运行，对照输出；文档或模板则按步骤走一遍。发现差异先修正，验证通过再发布。修订冲突时重读最新版本，核对差异并保留已有工作。包里只保留通用步骤、所需输入和权限，私有配置由使用者提供。

用 `report_skill_use` 反馈实际观察。用过第 1 版并发现规则错误，`corrected` 记在第 1 版；修好并验证了随后成功发布的第 2 版，`verified` 记在第 2 版。普通使用记 `used`，修订未知时留空。两个观察使用各自的 `request_id`，同一反馈因网络故障重试才复用 ID。以服务端回执确认反馈已记录。宿主拒绝写入时尊重决定，正常交付任务结果，简短说明反馈未记录。
